How the system is built

Security

Last updated 22 August 2026

Where things stand. The calculation engine, assurance checks and database layer are built and tested. Live HMRC submission and BACS payment await accreditation. This page describes how the system is designed, and is written to be handed to a security reviewer.

Where data lives

Every customer gets their own database. Not a shared table with an organisation column — a separate PostgreSQL database. A missing filter in application code cannot leak another company's payroll, because the other company's tables are not reachable from that connection. PostgreSQL refuses cross-database references outright.

This also makes several awkward things simple: restoring one customer without touching anyone else, giving a customer a complete export, and erasing them on request.

Customer payroll data is held in the United Kingdom. The database schema itself refuses to record any region outside the UK, so this is enforced rather than promised.

Encryption

  • In transit: TLS 1.2 or 1.3 for anything crossing a network.
  • At rest: bank details and integration credentials are encrypted at column level.
  • Keys are held in a managed key service. Each customer has their own key, so one compromised key exposes one customer.
  • Screens show only the last four digits of an account number. Full details are decrypted at one point only: building a payment file.

Who can read what

Inside every customer database there are three database roles, not one:

RoleCan doCannot do
ApplicationRead and write payroll recordsRead bank details
PaymentsRead bank details, to build a payment fileChange anything
ReportingRead payroll recordsWrite anything, or read bank details or credentials

The consequence worth noting: a compromise of the web application does not yield a list of employee bank accounts, because the application has never been able to read them.

What the database refuses to do

These are constraints and triggers in the database, so they hold even if application code is wrong:

  • A payroll run cannot be committed while any exception is undecided.
  • A committed payslip cannot be edited or deleted. Corrections create a new payslip that supersedes the old one, which is how RTI expects them anyway.
  • A committed run must record the named person who committed it.
  • A payslip that does not balance cannot be stored.
  • Audit tables reject updates and deletions entirely.
  • Salary, tax code, NI category and bank records cannot overlap in time, so any historic payslip can be reconstructed exactly.

Audit

Every change is recorded with who, what, when, and the before and after values. Audit tables are append-only at the database level — not by convention, by trigger. Records are retained for six years to match payroll record-keeping requirements.

Where an automation rule makes a change, the rule is named as the actor and the change is reversible from the log.

Automation limits

Routine corrections can be automated. Four things cannot be, whatever an administrator selects, because the limit is compiled into the software rather than left as a setting:

  • committing a payroll run
  • releasing a payment to someone recorded as a leaver
  • clearing a duplicate bank account
  • clearing negative net pay

No individual is scored, ranked or profiled. Nothing in the system constitutes an automated decision with legal or similarly significant effect under Article 22 of the UK GDPR.

Access to our own systems

  • Multi-factor authentication is required for any account that can approve a payroll run. This is enforced by the database, not by policy.
  • One owner per organisation, and the role cannot be silently removed.
  • Administrative access is not exposed to the public internet.

Backups

Each customer database is backed up separately every day and retained for 30 days, so one customer can be restored without affecting another.

We treat an untested restore as no backup at all. Restores are performed to a separate machine on a schedule to prove the backup can actually be used.

What is not finished

Stated plainly, because a reviewer will find these anyway:

  • HMRC RTI submission requires HMRC software recognition. In progress.
  • BACS payment submission requires a Service User Number from a sponsoring bank. In progress.
  • Cyber Essentials certification is not yet held.
  • Employee self-service is not enabled pending row-level security within customer databases.
  • National Insurance numbers are not yet encrypted at column level, unlike bank details.

Reporting a vulnerability

If you believe you have found a security problem, tell us through the enquiry form marked "security". We will acknowledge within two working days. Please give us a reasonable period to fix it before disclosing publicly. We will not pursue anyone who reports a genuine issue in good faith.
